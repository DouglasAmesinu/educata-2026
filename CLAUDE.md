# Educata 2026 registration app: instructions for Claude Code

Read this file fully before changing anything. It is the project's memory.

## What this is
An invite-only registration site for the Educata 2026 Content Creators Contest evening event (Delegation of German Industry and Commerce in Ghana). Each seat group gets one private link and a seat cap. Guests register, get a QR ticket (on screen, as a saved image, and by email), and are checked in at the gate by scanning the QR with a phone camera. Owner and only developer: Douglas Amesinu, sole IT administrator at the Delegation of German Industry and Commerce in Ghana. He is not a full-time developer, so explain changes in plain language and give exact click paths.

## Architecture (no build step, no bundler)
- Static site served by GitHub Pages at https://educata.gabsconnect.com/ (custom domain, DNS in Cloudflare, CNAME `educata` DNS-only). Plain HTML and ES modules.
- Firebase project id: `educata-2026`. Firestore database `(default)` is in region `europe-west1`. Auth: email and password.
- Firebase web SDK is loaded from `https://www.gstatic.com/firebasejs/10.12.2/...` (pinned). Do not change the version without testing. `scan.html` loads no Firebase at all (it talks to the scan relay functions with `fetch`).
- Scan relay: HTTPS functions `enrollDevice` and `relayScan` (`functions/relay.js`, same region) let staff phones send scans without a sign-in. See "Scan relay" below.
- Confirmation email: Cloud Function `sendConfirmation` (in `functions/`, Node 22, region from `TRIGGER_REGION`) writes a document to the `mail` collection. The Firebase extension "Trigger Email from Firestore" sends it by SMTP through Resend (sender domain `gabsconnect.com`). The browser never sends email.
- QR codes: vendored library `qrcode-lib.js` (MIT, Kazuhiko Arase). `qr.js` wraps it.

## Data model (Firestore)
- `groups/{gid}`: `name, category, cap, count, open, lastReg`. Public read. `count` only changes by +1 together with a registration create (rules enforce it).
- `invites/{CODE}`: `{gid}`. Public single `get`, no list. 10-character code, alphabet without 0 O 1 I L.
- `registrations/{lower-cased email}`: `gid, code, name, org, email, phone?, ref, createdAt` plus admin-written `checkedIn, checkedInAt, checkedInBy`. Doc id is the email, so one registration per email. `ref` looks like `EDU26-XXXXXX`. Guests can only create. Only admins read.
- `registrations` also get `undoneBy, undoneAt` from Undo check-in (admin only, same rule as check-in).
- `scans/{auto id}`: `ref, at, by`. Written by `relayScan` (admin SDK, `by` is the device id). The old rule still lets staff or admin create. Only admins read.
- `enrollCodes/{sha256 of the code}`: `createdAt, expiresAt (<= now + 10 min), used:false`. Admin create only, nobody reads or updates on the client; the function marks it used.
- `devices/{id}`: `tokenHash, label, createdAt, expiresAt, revoked, lastSeen, usedCode`-free (no code, no raw token). Created only by `enrollDevice`. Admin read, and admin update of `revoked` to true only.
- `enrollLimits/*`, `deviceLimits/{deviceId}`, `scanLimits/{ref}`: rate counters, function only, closed to every client.
- `staff/{uid}` and `admins/{uid}`: `{ok: true}`, created by hand in the console. Roles: guest (not signed in), staff (scan only; no page uses it any more, the owner may delete staff accounts), admin (everything).
- `mail/{id}`: written only by the Cloud Function. Nobody on the client can touch it.

## Scan relay (staff phones without a sign-in)
- `enrollDevice` POST `{code, label}`: looks up `enrollCodes/<sha256(code)>` in a transaction; refuses wrong, expired (min of expiresAt and createdAt + 5 min) or used codes; refuses at `MAX_DEVICES` active devices (409, code not consumed); creates `devices/{id}` with the SHA-256 of a random 32-byte base64url token, label (max 30), `expiresAt` now + `DEVICE_TTL_HOURS`; returns the raw token once. Limits: 5 attempts a minute per client (`enrollLimits/ip-<sha256(ip|minute)>`, raw IP never stored), 10 failures in total lock enrolment for 10 minutes (`enrollLimits/global`).
- `relayScan` POST `{ref}` with `Authorization: Bearer <token>`: 401 `{ok:false}` for a missing, revoked or expired token; 400 for a bad ref; 120 requests a minute per device (`deviceLimits`); 404 for an unknown ref; the same ref at most once per 3 s (`scanLimits`, 429 with Retry-After); writes `scans/{auto}` `{ref, at, by: deviceId}`; lastSeen at most once a minute. Answers only `{ok:true,status:"new"}` or `{ok:true,status:"checked_in",at:"HH:MM"}` (Africa/Accra, 24 h). Never any participant field.
- Both: CORS only for the `PUBLIC_BASE_URL` origin (others 403), POST and JSON only (405, 415), body at most 1 KB (413), bad JSON 400, `Cache-Control: no-store`, errors logged without the token.
- Settings in functions/.env: `MAX_DEVICES` (1 to 30, default 10), `DEVICE_TTL_HOURS` (1 to 720, default 48); `npm run check:env` checks them.
- Threat model (README Part 10 has the owner's version): both URLs are public. A stolen token can send scans (gate cards appear; staff still check the name) and learn whether a known reference is checked in and when; it cannot read names or details, check in, undo or enrol. Revoke on door.html > Scanning phones; tokens expire after DEVICE_TTL_HOURS anyway. CORS does not stop scripts; the token does. Anyone can trigger the 10-minute enrolment lock with wrong codes, so phones are set up the day before.
- Deploy order: rules, then functions (read the two Function URL lines), then config.js with RELAY_URL and ENROLL_URL plus scan.html, door.html, gate.js.

## The cap is enforced in the rules, not the page
Registration is one atomic commit: create `registrations/{email}` and bump `groups/{gid}.count` by exactly 1 and set `lastReg` to that email. index.html sends it as ONE `writeBatch` built from the live group snapshot (no reads first: the invite's gid comes from boot, so `tryRegister` gets `gid` and `group`). Only if the rules refuse it does the page read the group from the server (`getDocFromServer`): full or closed shows those messages, a changed count retries once with a transaction, an unchanged count means the email is already registered. The group listener ignores snapshots with `hasPendingWrites` and does not switch screens while submitting, or the guest taking the last seat would flash "All seats taken". Offline, a batch waits for the connection instead of failing: after 8 s the button says "Still connecting. Keep this page open...". `&debug=1` on an invite link shows a timings panel (labels and ms only). `firestore.rules` checks the invite code belongs to the group, the group is open, count stays <= cap, and no duplicate. Any change to registration fields or the cap logic MUST change `firestore.rules` and `test/rules.test.mjs` in the same change. Client-side checks are only for user experience.

## Gotchas already paid for (do not repeat)
- Firebase reserves env names such as `FUNCTION_REGION`. The setting is `TRIGGER_REGION`. The deploy tool did not reliably pass `.env` to analysis, so `functions/settings.js` reads `.env` itself.
- The function region, the extension location and the database must match: `europe-west1`. The extension install fails with "Database '(default)' does not exist in region" if they do not.
- Node 20 cloud runtime is blocked for new deploys after 30 October 2026. Keep Node 22.
- The extension's SMTP connection URI must contain the Resend key (`smtps://resend:KEY@smtp.resend.com:465`) or delivery fails with `Missing credentials for "PLAIN"`.
- A failed `mail` document is never retried: `confirm-<email>` is created once on purpose. To retest, delete that `mail` doc and re-register.
- Free-tier Firestore reads are limited. admin.html and door.html use live listeners: about 300 reads when opened, then one read per changed document. Never reload the whole list after an action.
- Brand colours: orange `#EC8223` is never text on white or grey (contrast 2.7). Orange buttons get black text. Change colours only in `assets/brand.css` and keep its `@pair` list true; `npm test` checks it.
- Event title: the official title is `EVENT_TITLE` in core.js ("Content Creators Contest", with the s). index.html, scan.html, and `EVENT_TITLE` in functions/.env must match it (the email has no title of its own: functions/compose.js takes it only from the `EVENT_TITLE` setting; a test checks that functions/.env.example holds the same value); `npm test` scans the whole project (and functions/.env) for any other spelling, and `npm run check:env` checks the setting. To rename: change core.js, then run `npm test` and fix every file it names, and change `EVENT_TITLE` in functions/.env and redeploy the function.
- Invite page hero: navy `#0A2232` (the banner's own background, `--navy` in brand.css) fading to black. The banner `assets/banner-source.jpg` must be a JPEG, 2.5 to 1: 1000 x 400 under 120 KB, or a larger original up to 2000 x 800 and 200 KB (`npm test` checks, and checks that the img width and height attributes in index.html equal the file's real size: update them if you replace the file). Its width is limited on short screens (`100vh - 560px` in the h1 rule) so the Full name field and the QR stay on the first screen at 1280 x 720 (400 px wide there; 1000 px on taller screens). The browser test reads the real pixels behind every hero text line and needs 4.5 contrast.
- Any text that depends on a dark background must set its own dark background in the same file. The live invite page once showed white hero text on the light grey page: index.html used `var(--navy)` but the live `assets/brand.css` was older, so the browser dropped the whole background rule. The hero now uses plain hex (`background-color:#0A2232` first, then the gradient) and every hero text sets its own colour; the browser tests load the page with brand.css blocked, with all of `assets/` blocked and with every CSS variable undefined, and measure the hero contrast each time.
- All site files (the eleven plus `assets/`) must come from the same version. A missing export in `config.js` blanks the admin or public page.
- Never edit functions/.env with `Set-Content -Encoding ascii` (ö becomes ?) or read it with `Get-Content` without `-Encoding UTF8` (PowerShell 5.1 reads ANSI and the next save makes mojibake such as Ã¶); `Out-File` and `>` in PowerShell 5.1 write UTF-16. Use Notepad or VS Code, or the one PowerShell block in README Part 9 (writes UTF-8 without BOM via [System.IO.File] and prints each non-ASCII code point). `npm run check:env` catches the damage. The email keeps non-ASCII intact end to end: tests build the raw message with nodemailer 6 (what the extension uses) and check the UTF-8 parts and RFC 2047 subject.
- The self-hosted Montserrat file is the latin subset (`unicode-range` U+0000-00FF and a few more): ö, é, ë, ü are in it, but the Ghanaian letters ɔ Ɔ ɛ Ɛ (U+0254, U+0186, U+025B, U+0190) are not, so in names they are drawn in the next font of the stack (system-ui: Segoe UI on Windows, San Francisco on iPhone, Roboto on Android) on the web pages and the saved ticket image. Readable, but a different style.
- Do not use em dashes in text.
- The email (including base64 images) is stored in one Firestore `mail` document (limit 1 MiB). Keep it under 600 KB: logo max 100 KB, banner max 140 KB, plus the QR and the .ics, HTML under 100 KB (Gmail clips larger). Tests assert this.
- The email uses the brand from DESIGN.md, in this order: a navy (`#0A2232`) band with the logo (at most 160 px, alt "educataGhana") and the presenter line (`EVENT_ORGANISER` presents) as live text, white 14 px, then the official banner at 600 px wide (alt text is `EVENT_TITLE`, styled white, bold, 28 px on a navy cell so it reads with images blocked; without the banner file, the title as live white bold text on navy), orange rule, headline and greeting, date card (orange date cell with black text from `EVENT_START_ISO`, Accra time), ticket card (orange top border, dashed divider, QR 220 px on white, reference in monospace), How it works, Add to calendar (Google button and attached `educata-2026.ics`, only when `EVENT_START_ISO` and `EVENT_END_ISO` are both set; the .ics never holds the guest's name or email), black footer with `EVENT_ORGANISER` exactly as typed. Headings are Arial bold. An email link cannot open an attachment, so the .ics is named in text, not a second button. Orange is never small text on white or grey (tests check it). The email body never shows the REPLY_TO address; it says "Questions? Simply reply to this email.". `EVENT_LINE` in functions/.env is not used by the email (config.js EVENT_LINE is the website's). The white logo `logo-light.png` sits straight on the navy band; the colour `logo.png` (dark grey letters) is used only without it, on a white panel.
- jsQR misreads tilted codes in noisy frames (dim light). The continuous scanner that needed a half-size retry is gone; if a camera scanner ever returns, test/scanner.test.mjs shows the retry is needed. Do not remove that test.
- Text typed by guests (name, organisation) must never be put into HTML with innerHTML (use textContent) or into an email subject or header. `escapeHtml` is used for the email body.
